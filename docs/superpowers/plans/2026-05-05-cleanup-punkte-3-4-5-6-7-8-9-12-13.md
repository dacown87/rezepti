## Key Changes

### 3. Chefkoch-Web-Plugin

- `fetchChefkoch()` bleibt der einzige Chefkoch-Pfad.
- `src/fetchers/web/chefkoch.ts` und die Chefkoch-Registry-Nutzung in `src/fetchers/web/index.ts` entfernen oder neutralisieren.
- Chefkoch-spezifische Tests ergaenzen, damit `classifyURL()` weiter `chefkoch` liefert und `processURL()` den dedizierten Fetcher nutzt.

### 4. TikTok OCR

- In `src/processors/llm.ts` einen internen Helper fuer reinen Vision-Text einfuehren, z. B. `extractVisibleTextFromImages(imageUrls, options)`.
- Kein `RecipeDataSchema.parse()` mehr fuer OCR-Frames.
- `extractTextFromVideoFrames()` sammelt bis `TIKTOK_MAX_OCR_FRAMES`, ruft den neuen Helper einmal auf und gibt Plaintext zurueck.
- Fehlerverhalten bleibt: kein ffmpeg, kein Frame oder LLM-Fehler ergibt `""`.

### 5. Logo-Asset 404

- Erst current-build Repro pruefen: aktueller Bundle verweist auf `/assets/public/Logo...png`, Datei existiert.
- Trotzdem robuste Server-Fallback-Route ergaenzen: Requests wie `/assets/Logo*.png` liefern `public/Logo.png`, statt SPA-HTML oder 404.
- Unit-/route-naher Test fuer Logo-Fallback und existierenden `/assets/public/...` Pfad.

### 6-8. Einkauf, Dictionary, Zutaten-Suche

- Route-Unit-Tests fuer `/api/v1/shopping`, `/api/v1/dictionary/match`, `/api/v1/recipes?ingredients=...`.
- DB-Integrationstests unter `TEST_DATABASE_URL` erweitern: Shopping CRUD, checked clear, dictionary alias match, OR/AND/threshold ingredient search.
- Dictionary-Verwaltungs-UI bleibt ausserhalb dieses Cleanup-PRs.

### 9. PDF-Export

- PDF-Logik fuer testbare Kernfunktionen auslagern: QR-URL, Dateiname, JSON-Parsing, Emoji-/Text-Sanitizing.
- Web/native PDF-Exporter nutzen diese Helper.
- Unit-Tests: Rezept ohne `source_url`, Umlaute/Sonderzeichen im Dateinamen/Text, QR-Wert `${serverUrl}/recipe/${id}`.

### 12. Docker Expo Web Build

- `Dockerfile` production baut den Expo-Web-Build selbst in einem `web-builder` Stage.
- Docker-Build darf nicht `postbuild:mobile` ausfuehren, weil im Container kein Git-Kontext garantiert ist.
- `docker-compose.yml` auf den aktuellen `Dockerfile` umstellen; `Dockerfile.react` nicht mehr als aktiver Buildpfad verwenden.
- CI Docker build nutzt weiter `target: production`, bekommt aber aktuellen Expo-Web-Output aus dem Build-Stage.

### 13. Supabase Cleanup

- Nicht Teil des Code-Cleanup-PRs.
- Separater manueller Ops-Schritt mit expliziter Zielumgebungs-Freigabe.
- Vor dem Delete immer Rezept und Abhaengigkeiten ausgeben:

```sql
select id, name, source_url from recipes where id = 36;
select count(*) as meal_plan_count from meal_plan where recipe_id = 36;
select count(*) as shopping_list_count from shopping_list where recipe_id = 36;
```

- Danach darf geloescht werden, auch wenn Rezept 36 nicht wie ein offensichtliches Testrezept aussieht:

```sql
begin;
delete from meal_plan where recipe_id = 36;
delete from shopping_list where recipe_id = 36;
delete from recipes where id = 36;
commit;
```

- Danach verifizieren:

```sql
select count(*) from recipes where id = 36;
select count(*) from meal_plan where recipe_id = 36;
select count(*) from shopping_list where recipe_id = 36;
```

### Engineering Review

Hohe Risiken:

- Supabase Cleanup ist in der aktuellen Form zu unsicher: hart codierte ID, keine Zielumgebungspruefung, keine Inhaltspruefung, keine Backup-/Rollback-Strategie. Vor dem Delete braucht es `select id, name, source_url from recipes where id = 36;`, Abhaengigkeitspruefung fuer `meal_plan` und `shopping_list`, erwartete Count-Ausgabe und `ON_ERROR_STOP`.
- Docker-Web-Build ist unterspezifiziert: `npm run build:mobile` triggert automatisch `postbuild:mobile`, das im Container wegen fehlendem Git-Kontext scheitern kann. Der `web-builder` muss Expo direkt ausfuehren oder ein separates `build:mobile:docker` nutzen.
- Ein einzelner PR fuer LLM, Docker, API-Tests, PDF-Refaktor, Static Serving und DB-Loeschung ist zu gross fuer sicheres Review.

Mittlere Risiken:

- TikTok-OCR braucht einen echten Plaintext-Vision-Pfad, nicht den bestehenden JSON-/RecipeData-Pfad. `chatJSON()` erzwingt JSON Response Mode; fuer OCR ist ein separater `chatText`-Helper oder ein bewusstes `{ text: string }` Schema noetig.
- OCR-Frame-Payload muss begrenzt werden: maximale Frame-Anzahl, Bildgroesse/JPEG-Qualitaet, Timeout und Test, dass alle ausgewaehlten Frames wirklich in den Vision-Request gehen.
- Logo-Fallback darf nicht Build-Probleme verstecken. Nur konkrete Logo-Miss-Pfade duerfen auf `public/Logo.png` fallen; andere fehlende Assets sollen weiter 404 liefern.
- API-Tests sollten auch Negativfaelle abdecken: malformed JSON, ungueltiger Threshold, sehr grosse Alias-Arrays, fehlende IDs, Route-Reihenfolge wie `/shopping/checked` vor `/:id`.
- PDF-Helper brauchen Paritaetstests fuer Web und Native, nicht nur isolierte Helper-Tests.

Zusaetzlicher Testbedarf:

- `photo-extraction.test.ts` Mock korrigieren, weil aktuell passing Tests Background-Fehler loggen.
- Ingredient Search mit `limit=abc`, negativen/zu grossen Limits und leerem `ingredients`.
- Shopping API mit invalidem JSON, fehlender `recipeId`, checked-clear Verhalten und Delete idempotency.
- Dictionary Match mit leerer Anfrage, sehr langer Anfrage, Alias-Treffern und Fuzzy-Treffern.
- TikTok OCR mit mehreren Frames, Helper-Fehler, ffmpeg fehlt, keine Frames.
- Static Assets: vorhandener hashed Logo-Pfad, konkreter Logo-Fallback, fremdes fehlendes Asset gibt 404 und kein HTML.
- Docker: Build plus Container-Smoke gegen `/api/v1/health`, `/`, `/extract`, `/Logo.png`, aktuellen hashed Logo-Pfad.

### DX Review

DX-Probleme, die vor Umsetzung in den Plan gehoeren:

- Fresh Clone ist nicht sauber beschrieben: Root `npm ci` installiert nicht `mobile/node_modules`. Expo Export braucht `cd mobile && npm ci`.
- `README.md` nennt `docker compose up`, aber die Compose-Services liegen hinter Profiles. Entweder muss plain `docker compose up` funktionieren oder die Doku muss auf `npm run docker:dev:build` wechseln.
- Healthcheck ist inkonsistent: Plan und Dockerfile nennen `/api/health`, die aktuelle API/Doku erwartet `/api/v1/health`.
- DB-Testworkflow ist nicht reproduzierbar genug: `TEST_DATABASE_URL=...` reicht nicht; Schema Push, lokale Test-DB und klare Skip-/Fail-Regeln muessen dokumentiert sein.
- Supabase Delete braucht einen ausfuehrbaren Weg, z. B. `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f scripts/delete-recipe-36.sql`, plus Schutz gegen falsche Zielumgebung.
- Testbefehle sollten standardisiert werden: `npm run test:unit`, `npx vitest run test/unit/db-react.test.ts`, CI-equivalent `npm test -- --run --exclude="test/e2e/**"`.
